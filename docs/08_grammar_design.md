# ResumeLens – Candidate Profile Language (Context-Free Grammar with textX)

## 1. Purpose of the Stage

Stages 1 to 3 produce Python objects: the extracted data (`ExtractedData`), the normalized data (`NormalizedData`), and the classification (`{profile: ACCEPTED / REJECTED}`). Stage 4 defines a **domain-specific language (DSL)** to represent that information in a structured, readable, and verifiable way: the **candidate profile language**.

The purpose of this component is different from extraction, normalization, and recognition. The grammar does not analyze the résumé; it defines **how the resulting candidate information must be structurally represented**, and rejects any representation that does not follow that structure.

```text
Résumé text
   -> Stage 1 (regex) -> Stage 2 (FST) -> Stage 3 (automata)
   -> ProfileGenerator:  writes the candidate profile in the DSL
   -> ProfileValidator:  textX checks the grammar (and semantic rules)
   -> ProfileVisualizer: HTML of the candidate (only for valid profiles)
```

### 1.1 Requirements of the Stage

| Requirement of the statement | Where |
| :--- | :--- |
| Define the grammar using EBNF, identifying terminals and non-terminals | Sections 3 and 4 |
| Explain the structural characteristics of the language | Section 5 |
| Implement the grammar using textX | `src/model/grammar/resume_lens.tx` (Section 6) |
| Language with personal information, contact, experience, skills, and classification result | Sections 2 and 3 |
| Structured and repeated elements (several experiences, education records, skills) | Section 5.2 |
| Validate generated candidate profiles | `ProfileGenerator` + `ProfileValidator` (Sections 7 and 8) |
| Reject representations that violate the lexical or syntactic rules | Section 8 |
| Generate the visualization output | Section 9 |

## 2. The Candidate Profile Language

A profile is a `candidate` block with the name of the candidate and nested blocks for each kind of information. Example (Wednesday Addams, generated by ResumeLens from the example of the statement):

```text
candidate "Wednesday Addams" {
    contact {
        email wednesday@mail.com
        phone +57 300 1234567
    }
    experience {
        years 3
        entry "3 years of experience"
    }
    education {
        degree BACHELOR
        field COMPUTER_SCIENCE
    }
    skills {
        languages: JAVASCRIPT
        frameworks: REACT, NODE_JS
        databases: POSTGRESQL
        tools: GIT
    }
    classification {
        FULL_STACK_DEVELOPER: ACCEPTED
        MACHINE_LEARNING_ENGINEER: REJECTED
        CYBERSECURITY_ENGINEER: REJECTED
        DATA_ENGINEER: REJECTED
    }
}
```

Origin of each block:

| Block | Information | Comes from |
| :--- | :--- | :--- |
| `candidate "..."` | Personal information (name) | `NormalizedData.name` (stage 1) |
| `contact` | Emails and phones | `NormalizedData.emails`, `phones` (stage 1) |
| `experience` | Years of experience and each experience expression | `experience_years` (`M_EXP`) and `experience_entries` (stage 2) |
| `education` | Degrees and fields of study | `academic_qualifications` (`M_ACAD`, stage 2) |
| `skills` | Normalized qualifications by category | `programming_languages`, `frameworks_libraries`, `databases`, `tools_technologies`, `other_qualifications` (stage 2) |
| `classification` | Result of each profile automaton | `ProfileAutomata.classify` (stage 3) |

Profile files use the extension `.rl` (ResumeLens). Examples: `data/profiles/`.

## 3. Grammar in EBNF

The grammar is `G = (V, Σ, P, S)`, where `V` is the set of non-terminals (Section 4.2), `Σ` the set of terminals (Section 4.1), `P` the productions below, and `S = CandidateProfile` the initial symbol.

Notation: `"x"` is a literal terminal, `[ X ]` is optional (0 or 1), `{ X }` is repetition (0 or more), `|` is alternative.

```ebnf
CandidateProfile ::= "candidate" STRING "{"
                         Contact
                         [ Experience ]
                         [ Education ]
                         [ Skills ]
                         Classification
                     "}"

Contact          ::= "contact" "{" { Email } { Phone } "}"
Email            ::= "email" EMAIL
Phone            ::= "phone" PHONE

Experience       ::= "experience" "{" "years" INT ExperienceEntry { ExperienceEntry } "}"
ExperienceEntry  ::= "entry" STRING

Education        ::= "education" "{" EducationItem { EducationItem } "}"
EducationItem    ::= Degree | Field
Degree           ::= "degree" DegreeName
Field            ::= "field" TOKEN
DegreeName       ::= "BACHELOR" | "MASTER" | "PHD"

Skills           ::= "skills" "{" SkillCategory { SkillCategory } "}"
SkillCategory    ::= CategoryName ":" TOKEN { "," TOKEN }
CategoryName     ::= "languages" | "frameworks" | "databases" | "tools" | "other"

Classification   ::= "classification" "{" ProfileResult { ProfileResult } "}"
ProfileResult    ::= ProfileName ":" Result
ProfileName      ::= "FULL_STACK_DEVELOPER" | "MACHINE_LEARNING_ENGINEER"
                   | "CYBERSECURITY_ENGINEER" | "DATA_ENGINEER"
Result           ::= "ACCEPTED" | "REJECTED"
```

Lexical rules (terminals defined by regular expressions):

```ebnf
STRING  ::= '"' { any character except '"' } '"'
INT     ::= digit { digit }
TOKEN   ::= /[A-Z][A-Z0-9_]*/
EMAIL   ::= /[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}/
PHONE   ::= /[+(]?[0-9][0-9 ().-]*[0-9]/
COMMENT ::= /\/\/.*$/          (ignored)
```

## 4. Terminals and Non-Terminals

### 4.1 Terminals (Σ)

| Kind | Terminals |
| :--- | :--- |
| Keywords of the blocks | `candidate`, `contact`, `email`, `phone`, `experience`, `years`, `entry`, `education`, `degree`, `field`, `skills`, `classification` |
| Category names | `languages`, `frameworks`, `databases`, `tools`, `other` |
| Fixed values | `BACHELOR`, `MASTER`, `PHD`, `FULL_STACK_DEVELOPER`, `MACHINE_LEARNING_ENGINEER`, `CYBERSECURITY_ENGINEER`, `DATA_ENGINEER`, `ACCEPTED`, `REJECTED` |
| Punctuation | `{`, `}`, `:`, `,` |
| Lexical tokens (regular expressions) | `STRING`, `INT`, `TOKEN`, `EMAIL`, `PHONE` |

The lexical tokens are terminals of the grammar, but each one represents a regular language (for example, `TOKEN` is any word of capital letters, digits, and underscores that starts with a letter). textX recognizes them with the regular expressions of Section 3.

### 4.2 Non-terminals (V)

| Non-terminal | Represents |
| :--- | :--- |
| `CandidateProfile` | The complete profile (initial symbol) |
| `Contact`, `Email`, `Phone` | Contact information |
| `Experience`, `ExperienceEntry` | Professional experience |
| `Education`, `EducationItem`, `Degree`, `Field`, `DegreeName` | Education records |
| `Skills`, `SkillCategory`, `CategoryName` | Skills grouped by category |
| `Classification`, `ProfileResult`, `ProfileName`, `Result` | Result of the classification |

`DegreeName`, `CategoryName`, `ProfileName`, and `Result` only produce terminals (alternatives of fixed words). In textX they are *match rules*: they return the matched text instead of an object.

## 5. Structural Characteristics of the Language

### 5.1 Hierarchy and order

- A profile has **one root block** (`candidate`) with the name and **up to five nested blocks**.
- The blocks have a **fixed order**: `contact`, `experience`, `education`, `skills`, `classification`. A profile with the blocks in another order is rejected.
- Every block is delimited by `{` and `}`, and each `{` must be closed by its `}`.

### 5.2 Mandatory, optional, and repeated elements

| Element | Multiplicity | Reason |
| :--- | :--- | :--- |
| `contact` | exactly 1 (it may be empty) | Every profile has a contact section, even if no email or phone was found |
| `email`, `phone` | 0 or more each | A résumé can contain several emails and phones |
| `experience` | 0 or 1 | A résumé may not mention explicit years of experience |
| `entry` | 1 or more (inside `experience`) | **Multiple professional experiences**: one per expression found in the résumé |
| `education` | 0 or 1 | |
| `degree` / `field` | 1 or more (inside `education`) | **Multiple education records** |
| `skills` | 0 or 1 | |
| skill category | 1 or more (inside `skills`) | One line per non-empty category |
| `TOKEN` of a category | 1 or more, separated by `,` | **Multiple skills** per category |
| `classification` | exactly 1 | The result of stage 3 is always required |
| `PROFILE: RESULT` | 1 or more (the four profiles, see Section 8.3) | One result per profile |

### 5.3 Why a context-free grammar

- The language is **hierarchical**: blocks contain blocks, lists, and values. A context-free grammar describes this structure directly with one production per block, and its derivation tree has exactly the shape of the profile (`CandidateProfile` → `Skills` → `SkillCategory` → `TOKEN`). textX uses that tree to build the **model** (Python objects) that the visualization reads.
- Every production has **a single non-terminal on the left side**, so each block is defined in the same way wherever it appears. This is the definition of a context-free grammar.
- Each block starts with a **different keyword**, so for every input there is only one possible derivation: the grammar is **not ambiguous**.
- Note: in this DSL the nesting depth is bounded (at most two levels of blocks inside `candidate`), so the set of valid strings could, in theory, also be described by a very long regular expression. A regular expression, however, only answers "matches / does not match": it does not give the hierarchical structure. The context-free grammar is used because it defines the structure of the profile and produces the parse tree from which the model is built, which is what this stage needs.

## 6. Implementation with textX

### 6.1 Grammar file

`src/model/grammar/resume_lens.tx`. The translation from EBNF to textX is direct:

| EBNF | textX | Meaning |
| :--- | :--- | :--- |
| `X ::= "a" Y` | `X: 'a' y=Y ;` | Rule; `y=` stores the result as an attribute of the object |
| `[ Y ]` | `(y=Y)?` | Optional |
| `{ Y }` | `ys*=Y` | Zero or more (list) |
| `Y { Y }` | `ys+=Y` | One or more (list) |
| `TOKEN { "," TOKEN }` | `tokens+=TOKEN[',']` | List separated by commas |
| `Y \| Z` | `Y \| Z` | Alternative |
| regular expression | `/.../` | Lexical rule |

Fragment:

```text
CandidateProfile:
    'candidate' name=STRING '{'
        contact=Contact
        (experience=Experience)?
        (education=Education)?
        (skills=Skills)?
        classification=Classification
    '}'
;

SkillCategory:
    category=CategoryName ':' tokens+=TOKEN[',']
;

Result:
    'ACCEPTED' | 'REJECTED'
;

TOKEN:
    /[A-Z][A-Z0-9_]*/
;
```

The rule named `Comment` is special in textX: everything it matches (`// ...`) is ignored, so the profile files can contain comments.

### 6.2 Model

When a profile is valid, textX returns the **model**: the profile as Python objects with the attributes of the grammar.

```python
model = ProfileValidator().validate(text)

model.name                                   # "Wednesday Addams"
model.contact.emails[0].value                # "wednesday@mail.com"
model.experience.years                       # 3
model.experience.entries[0].text             # "3 years of experience"
model.skills.categories[1].category          # "frameworks"
model.skills.categories[1].tokens            # ["REACT", "NODE_JS"]
model.classification.results[0].profile      # "FULL_STACK_DEVELOPER"
model.classification.results[0].result       # "ACCEPTED"
```

The optional blocks that are not present are `None` (for example, `model.skills is None`).

### 6.3 Files

```text
src/model/grammar/
    resume_lens.tx            # grammar of the candidate profile language
    profile_generator.py      # class ProfileGenerator: data of stages 1-3 -> DSL text
    profile_validator.py      # class ProfileValidator: textX + semantic rules

data/profiles/                # example profiles (.rl), valid and invalid

tests/grammar/
    test_profile_generator.py

src/visualization/

```

## 7. Generation of the Profile (`ProfileGenerator`)

`ProfileGenerator.generate(normalized, classification)` writes the DSL text from the result of stages 2 and 3:

```python
extracted = extract_resume_information(text)              # stage 1
normalized = ResumeNormalizer().normalize(extracted)      # stage 2
classification = ProfileAutomata().classify(normalized)   # stage 3
profile = ProfileGenerator().generate(normalized, classification)   # stage 4
```

Rules of the generator:

- **Name:** if stage 1 did not find it, `"Unknown candidate"` is written (the grammar requires a name).
- **Contact:** always present; one `email` and one `phone` line per value. A phone extracted across a line break is written in one line.
- **Experience:** only if there are experience entries; `years` is the maximum produced by `M_EXP`, followed by one `entry` per expression.
- **Education:** only if there are academic tokens; `BACHELOR`, `MASTER`, and `PHD` are written as `degree`, the others (`COMPUTER_SCIENCE`, ...) as `field`.
- **Skills:** only the non-empty categories, in the order languages, frameworks, databases, tools, other. `SQL` can appear in `languages` and in `databases`, as in stage 2.
- **Classification:** always the four profiles, in the order of `ProfileVocabulary`.

The generated text is then validated by `ProfileValidator`, so an error in the generator can never produce an invalid profile in the visualization.

## 8. Validation (`ProfileValidator`)

`ProfileValidator` loads the grammar with `metamodel_from_file` and validates a text with `model_from_str` (or a file with `model_from_file`). There are three kinds of errors. The messages below are the real messages produced by textX (`line:column`).

### 8.1 Lexical errors

A part of the text is not a valid token where it appears. textX raises `TextXSyntaxError`.

| Invalid input | Message |
| :--- | :--- |
| `frameworks: react, NODE_JS` | `16:21: Expected TOKEN => 'ameworks: *react, NOD'` |
| `DATA_ENGINEER: MAYBE` | `24:24: Expected 'ACCEPTED' or 'REJECTED'` |
| `email wednesday.mail.com` | `3:15: Expected EMAIL` |
| `years three` | `7:15: Expected INT` |
| `degree DIPLOMA` | `11:16: Expected 'BACHELOR' or 'MASTER' or 'PHD'` |
| `candidate Wednesday {` (name without quotes) | `1:11: Expected STRING` |

### 8.2 Syntactic errors

The tokens are valid, but the structure is not the one defined by the grammar. textX raises `TextXSyntaxError`.

| Invalid input | Message |
| :--- | :--- |
| The `classification` block is missing | `20:1: Expected 'classification'` |
| The last `}` is missing | `26:1: Expected '}'` |
| `skills` written before `contact` | `2:5: Expected 'contact'` |
| A category without tokens (`tools:`) | `19:5: Expected TOKEN` |
| `experience` without any `entry` | `8:5: Expected 'entry'` |

### 8.3 Semantic errors

The text satisfies the grammar, but its content is not consistent with ResumeLens. These rules are implemented as **object processors** of textX (functions that textX calls for each object while it builds the model). They raise `TextXSemanticError`, also with the location.

| Rule | Invalid input | Message |
| :--- | :--- | :--- |
| Every token belongs to the canonical vocabulary of its category (`NormalizationVocabulary`) | `tools: GIT, MYSQL` | `18:9: "MYSQL" is not a valid token of the category "tools"` |
| | `tools: PYTHON` | `18:9: "PYTHON" is not a valid token of the category "tools"` |
| A field of study is a canonical academic field | `field BIOLOGY` | `12:9: "BIOLOGY" is not a valid field of study` |
| A skill category appears once | two `tools:` lines | `14:5: repeated skill category: tools` |
| Each profile appears exactly once | `FULL_STACK_DEVELOPER` twice | `20:5: repeated profile: FULL_STACK_DEVELOPER` |
| | `DATA_ENGINEER` missing | `20:5: missing profile: DATA_ENGINEER` |

### 8.4 Example files

| File | Result |
| :--- | :--- |
| `data/profiles/valid_wednesday_addams.rl` | Valid (Full Stack example of the statement) |
| `data/profiles/valid_mary_jane_watson.rl` | Valid (Machine Learning example of the statement) |
| `data/profiles/invalid_lexical.rl` | Lexical error (`react` in lower case) |
| `data/profiles/invalid_syntax.rl` | Syntactic error (`classification` missing) |
| `data/profiles/invalid_semantic.rl` | Semantic error (`MYSQL` is not in the vocabulary) |

## 9. Visualization Output

Once a profile has been validated, `ProfileVisualizer` (`src/visualization/profile_visualizer.py`) builds a short **HTML** page of the candidate. This is the visualization output required by the statement.

### 9.1 Input: the textX model, not the text

`ProfileVisualizer.render(model)` receives the **model** returned by `ProfileValidator` (Section 6.2), never the raw `.rl` text:

```python
model = ProfileValidator().validate(profile)     # grammar + semantic rules
html = ProfileVisualizer().render(model)         # visualization
```

This guarantees that only profiles that satisfy the lexical, syntactic, and semantic rules are visualized. An invalid profile raises an error in `validate` and never reaches the visualizer. It also means the visualizer does not parse anything: it only reads the attributes of the model (`model.name`, `model.contact.emails`, `model.skills.categories`, ...).

### 9.2 Content of the page

| Section | Taken from the model | Shown as |
| :--- | :--- | :--- |
| Name | `model.name` | Page title (`<h1>`) |
| Contact | `model.contact.emails`, `model.contact.phones` | List `Email: ...`, `Phone: ...` |
| Experience | `model.experience.years`, `model.experience.entries` | Years in bold and one item per entry |
| Education | `model.education.items` (`Degree` or `Field`) | List `Degree: BACHELOR`, `Field: COMPUTER_SCIENCE` |
| Skills | `model.skills.categories` | Table with one row per category and one label per token |
| Classification | `model.classification.results` | Table with the four profiles; the `ACCEPTED` rows are highlighted in green |

The optional blocks of the grammar (`experience`, `education`, `skills`) are `None` in the model when they are missing; in that case the section shows *Not reported*. The page is a single self-contained file (the CSS is inside a `<style>` tag), so it can be opened directly in a browser.

### 9.3 Escaping of special characters

The values written by the candidate (name, emails, experience entries) can contain characters with a meaning in HTML. A `STRING` of the grammar accepts, for example, `"Tom <b>Admin</b> & Co"`. Every value is escaped with `html.escape` before it is inserted in the page:

| Value in the model | Written in the HTML |
| :--- | :--- |
| `Tom <b>Admin</b> & Co` | `Tom &lt;b&gt;Admin&lt;/b&gt; &amp; Co` |
| `2 years <script> & R&D` | `2 years &lt;script&gt; &amp; R&amp;D` |

So the browser shows the text exactly as it was written and never interprets it as HTML or JavaScript.

### 9.4 Example

For `data/profiles/valid_wednesday_addams.rl` the page shows the name *Wednesday Addams*, her email and phone, 3 years of experience, `BACHELOR` and `COMPUTER_SCIENCE`, the tokens `JAVASCRIPT`, `REACT`, `NODE_JS`, `POSTGRESQL`, and `GIT` grouped by category, and the classification table with `FULL_STACK_DEVELOPER: ACCEPTED` highlighted and the other three profiles `REJECTED`.
